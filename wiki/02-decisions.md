# 주요 설계 결정

코드만 보면 "왜 이렇게 했지?" 싶은 판단들의 이유. **함부로 되돌리면 안 되는 것들**이 많다.

## 포지셔닝

- **우리는 "측정 도구 제공자"지 "측정 서비스"가 아니다.** 측정 기준·정확도·가격은 헬스장 책임. 이래서 클레임이 우리가 아닌 헬스장으로 가고, 업종 확장(크루/이벤트/마라톤)이 열린다. 표준 템플릿은 "예시"일 뿐 강제 아님.

## 인증/계정

- **로그인 식별자 = 아이디(USERNAME).** 초기엔 휴대폰이었으나 아이디로 일원화(회원·트레이너·사장 공통). 휴대폰은 식별자에서 **연락처+사람식별**로 성격 변경.
- **claim = 익명 회원이 계정(아이디+비번)을 만드는 것.** 소유권 이전이 아니라 "이 번호로 쌓인 기록을 볼 열쇠를 만드는 것". 생애 최초 1회.
- **"로그인해서 연결(link)" 로직은 폐기됨.** 전화번호로 자동 통합되므로 수동 연결 불필요. 이미 계정 있으면 그냥 로그인하면 자기 피드가 보인다.
- **떠도는 계정 허용** — 가입만 하고 클럽 없는 상태 OK. 로그인은 되고, 클럽 없으면 `/me`(회원 피드)나 랜딩으로. 클럽 소속(role)은 인증과 분리 — `LoginMemberService`가 membership 없어도 인증 성공시킴.

## 무료 한도

- **기준 = claim한 회원 수** (등록 회원 전체가 아님). 익명 등록·측정은 무제한.
- **claim한 회원은 사장이 휴면 처리 불가**(본인 소유 데이터 보호 + 무료 회피 방지). 익명 회원만 관리 가능.
- 이유: 사장이 회원을 치워서 무료 유지하는 것을 막고, 회원의 가입 욕구가 유료 압력이 되게.

## 전화번호 통합 (성장 엔진의 핵심)

- 회원 등록 시 **전화번호 필수**. 그 번호의 Member 있으면 재사용(통합), 없으면 생성.
- 번호는 **숫자만 정규화**해서 저장(`010-1234`, `01012345678` 동일 취급).
- 같은 번호가 여러 클럽에 등록되면 → 한 Member에 Membership 여러 개 → 회원 피드에서 시간순 통합.
- **격리 필수** — 클럽은 `currentClub.clubId()`로 자기 클럽 Membership만 조회. B헬스장 화면에 A헬스장 기록/존재가 절대 안 보임. 통합은 Member 레벨(회원 본인만 봄).

## 권한 층위

- 5단계: ROLE_ADMIN(운영자) / OWNER(사장) / STAFF(트레이너) / MEMBER(회원) / USER(떠도는).
- **운영자는 불리언(`Member.platformAdmin`) 하나로 시작.** 영업직 등 다층 권한은 실제 필요해질 때 enum→RBAC로. 지금 RBAC는 과설계(운영자 아직 1명).
- 권한 부여 단일 지점: `LoginMember.getAuthorities()`. 여기만 바꾸면 확장 가능.
- `/admin/**`=ADMIN, `/owner/**`=OWNER, 클럽 화면=OWNER/STAFF. 메뉴 숨김(`sec:authorize`)만으론 부족 — URL 접근제어(`hasRole`)가 진짜 방어선.

## 리텐션

- **"미용실식 정기 점검"** — 측정 주기(cadence)로 "측정할 때 됐어요" 유도. 측정 주기 = 방문 주기.
- 다음 측정 예정일·상태(정상/임박/지연/이탈위험)는 **저장 안 하고 조회 시 계산**(배치 불필요, 항상 정확).

## 결제

- **PG 연동 없음. 수기 계약.** 운영자가 `/admin`에서 클럽 plan을 FREE↔PAID 수동 토글.
- 요금제 화면(`/owner/plans`)은 목업. 가격(5/9/15만원)은 예시 — 실제는 헬스장 3곳 검증 후 확정.
- 실제 결제는 계약 헬스장이 생긴 뒤 붙임.

## UI 방향

- **htmx 부분 갱신** — SPA 없이 목록/카드 갱신. `layout :: fragment` 반환.
- **공유 카드/claim/로그인/랜딩/클럽생성은 layout 미적용**(독립 페이지) — 회원이 보는 외부 페이지거나 로그인 전이라 앱 네비가 있으면 안 됨.
- 그 외 앱 화면은 전부 `layout.html` 상속.

## 커뮤니티

- **자유게시판 안 만듦.** 죽은 게시판 리스크·모더레이션 비용·정체성 흐림. 대신 측정 데이터 기반 랭킹/공유/챌린지로 상호작용 리텐션 취함.
